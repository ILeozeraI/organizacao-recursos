# DEF-002 — Deadlock no PostgreSQL vira HTTP 500 em reservas simultâneas do mesmo professor

| Campo | Valor |
|---|---|
| Status | Fechado |
| Severidade | **Alta** — requisição válida recebe 500 (erro interno) sob concorrência; afeta o RF6 e a disponibilidade |
| Prioridade | **P1** — limitador de nota ("possibilidade de dupla reserva"/robustez); corrigir antes da release candidate |
| Encontrado em | CI run 43467786082 (push na `main`), teste `ConcorrenciaReservaIT.mesmoProfessorEmSalasDiferentes()[1]` |
| Frequência | Intermitente: 1 de 5 repetições nessa execução; não apareceu na execução anterior (run 43467171777) |
| Requisito / risco | RF5, RF6, RNF-ROB-01 (criação de reserva só responde 201 ou 409, nunca 500) |
| Responsável | Leonardo Cavalcanti da Silva |

## Ambiente
- GitHub Actions `ubuntu-latest`, Java 21, PostgreSQL 16 (Testcontainers), dados fictícios.

## Pré-condições
- 20 salas livres; Prof. Carla (recurso 6) sem reservas.

## Passos mínimos
1. Disparar ao mesmo tempo (CountDownLatch) 20 `POST /reservas`, cada um numa sala diferente,
   todos com `professorId = 6` e o mesmo horário (2026-12-01 10h–12h).

## Esperado × obtido
| Esperado | Obtido |
|---|---|
| 1 resposta 201 e 19 respostas 409 | Algumas respostas **500** (`ERRO_INTERNO`) |

## Evidência (log sanitizado)
```
SQLState: 40P01  ERROR: deadlock detected
  Process 70 waits for ShareLock on transaction 1663; blocked by process 63.
  while checking exclusion constraint on tuple (0,1) in relation "reserva"
TratadorDeErros : Erro inesperado
org.springframework.dao.CannotAcquireLockException: could not execute statement [ERROR: deadlock detected ...]
```

## Causa raiz (5 porquês)
1. Por que 500? A exceção `CannotAcquireLockException` (SQLState `40P01`) não era tratada e caiu no tratador genérico.
2. Por que houve deadlock? Com **duas** constraints `EXCLUDE` (sala e professor), transações concorrentes
   esperam umas pelas outras ao checar tuplas ainda não confirmadas; o PostgreSQL detecta o ciclo e
   aborta uma delas (comportamento documentado do banco).
3. Por que o código não previu isso? O tratamento só reconhecia `23P01` (violação de exclusão).
4. Por que não apareceu antes? É intermitente: depende do entrelaçamento exato das threads.
5. Aprendizado: sob concorrência, além de "conflito" (23P01) existe "vítima de deadlock" (40P01), que é
   **transitória** e deve ser repetida — não exibida ao usuário como erro interno.

## Correção
- `ReservaService.comProtecaoDeConcorrencia`: se a falha for `40P01` (deadlock) ou `40001`
  (serialização), a operação é **repetida** (até 3 tentativas, com pequena espera crescente).
  Na repetição, a constraint passa a enxergar a reserva já confirmada e responde `23P01` → **409**.
- Teste de regressão: `ConcorrenciaReservaIT` (repetido 5× por execução, com 10 cenários).

## Critério de verificação
- `./mvnw -B verify` verde no CI em execuções seguidas, sem nenhum 500 no `ConcorrenciaReservaIT`.
