# DEF-001 — Timeout da notificação é classificado como "resposta inválida"

| Campo | Valor |
|---|---|
| Status | Fechado |
| Severidade | Média — falha de notificação fica registrada com motivo errado; diagnóstico e futura política de retry seriam enganados |
| Prioridade | P2 — corrigir antes da release candidate |
| Encontrado em | CI run 43466967764 (commit da suíte de testes), teste `HttpNotificacaoClientTest.timeout` (INT-04) |
| Requisito / risco | RF11, RNF-INT-01 (provedor lento não pode ser confundido com contrato quebrado) |
| Responsável | Leonardo Cavalcanti da Silva |

## Ambiente
- GitHub Actions `ubuntu-latest`, Java 21 (Temurin), WireMock em porta aleatória.
- Dados sintéticos; token `token-de-teste` (fictício).

## Pré-condições
- Provedor de notificação (WireMock) responde `200` com corpo válido, porém com atraso fixo de 2000 ms.
- Cliente configurado com `read-timeout` de 800 ms.

## Passos mínimos
1. Chamar `HttpNotificacaoClient.enviar(...)`.

## Esperado × obtido
| Esperado (INT-04) | Obtido |
|---|---|
| `IntegracaoException` do tipo `INDISPONIVEL` | `IntegracaoException` do tipo `RESPOSTA_INVALIDA` |

## Evidência (sanitizada)
```
HttpNotificacaoClientTest.timeout:85 [Extracted: tipo]
expected: INDISPONIVEL
 but was: RESPOSTA_INVALIDA
```

## Causa raiz (5 porquês)
1. Por que veio `RESPOSTA_INVALIDA`? Porque a exceção caiu no `catch (RestClientException)`.
2. Por que não caiu no `catch (ResourceAccessException)`? Porque o estouro de tempo aconteceu **durante a leitura do corpo**, e o `RestClient` embrulha esse `SocketTimeoutException` em `RestClientException` genérica.
3. Por que o código não previu isso? Porque assumimos que todo erro de I/O vira `ResourceAccessException`.
4. Por que a suposição não foi verificada antes? Porque não havia teste de timeout até o INT-04.
5. Aprendizado: classificar pela **causa** (I/O) e não só pelo tipo da exceção externa.

## Correção
- `HttpNotificacaoClient`: no `catch (RestClientException)`, se a cadeia de causas contém erro de rede (`SocketTimeoutException`/`SocketException`)
  (ex.: `SocketTimeoutException`), classificar como `INDISPONIVEL`.
- Teste de regressão: o próprio `HttpNotificacaoClientTest.timeout` (INT-04).

## Critério de verificação
- `./mvnw -B verify` verde no CI, com INT-04 passando.

> Observação da correção: a primeira ideia (tratar qualquer `IOException`) foi descartada antes do
> commit final porque o erro de JSON malformado do Jackson **também** é `IOException`, o que quebraria
> o INT-05. A classificação usa apenas `SocketTimeoutException`/`SocketException`.
